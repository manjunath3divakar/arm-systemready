# SystemReady ACS Results Directory Structure (SR and DT)

This guide explains **where SystemReady ACS results are stored and what each results folder contains**. It applies to both **SystemReady SR** (ACPI-based SystemReady band) and **SystemReady-DT** (Devicetree band). Band-specific results and requirements are identified explicitly.

This is a **results-layout reference**, not a template generator: it does not create folders, require empty placeholders, or replace the test instructions for either band. Retain the directories and original logs actually generated by the ACS version you run.

For test execution, see the [SystemReady SR flow](systemready_band_flow.md) or [SystemReady-DT flow](systemready_devicetree_band_flow.md). For Linux and WinPE OS diagnostics, see the [combined OS scripts guide](../common/os_scripts/README.md).

## 1. ACS results on the test media

Both bands write their automated results under `acs_results_template/acs_results/` on the ACS results partition. The exact set of folders varies with the **band, enabled suites, hardware, and ACS release**.

```text
acs_results_template/
├── acs_results/
│   ├── acs_summary/
│   ├── app_output/
│   ├── edk2-test-parser/
│   ├── fwts/
│   ├── linux/
│   ├── linux_acs/
│   ├── linux_dump/
│   ├── linux_tools/
│   ├── post-script/
│   ├── sct_results/
│   ├── uefi/
│   ├── uefi_dump/
│   ├── bbsr/                 # when BBSR is enabled
│   ├── sbmr/                 # SR only, when SBMR is enabled
│   └── network_boot/         # DT only, when network boot is tested
├── fw/                       # supplementary firmware evidence
└── os-logs/                  # installed-OS test evidence
```

The paths above are **examples of possible output**, not a list of folders that must appear after every run. Older results may also contain names such as `scrt_results/`. Do not rename or fabricate test output just to make it resemble this example.

### `./acs_results/`

Copy or retain the **entire ACS-generated `acs_results` folder**, including logs, summaries, configuration snapshots, failure details and any optional subfolders. In particular, preserve original test logs rather than submitting only a summary PDF or HTML report.

| Subdirectory | What it contains | Band / condition |
| --- | --- | --- |
| `acs_summary/` | Parsed ACS reports, JSON/HTML/PDF summaries and configuration snapshots (when generated). | SR and DT |
| `app_output/` | Output from UEFI applications, for example capsule/FMP/ESRT utilities. | When the relevant apps run |
| `edk2-test-parser/` | Parsed UEFI SCT summaries and diagnostic logs. | SR and DT, where SCT parsing runs |
| `fwts/` | Firmware Test Suite (FWTS) test logs; SR normally uses SBBR-oriented tests, DT uses EBBR-oriented tests. | SR and DT |
| `linux/`, `linux_acs/` | Linux-stage ACS test output, including BSA results; exact names depend on the image. | SR and DT; layout varies |
| `linux_dump/` | Firmware, kernel and platform data collected **inside the ACS Linux environment**. | SR and DT |
| `linux_tools/` | Logs from additional Linux tools and checks (for example, Devicetree validation, kselftests or other platform checks). | As enabled; DT has DT-specific checks |
| `post-script/` | Results-folder and post-run validation output, such as `post-script.log`. | When enabled |
| `sct_results/` | UEFI SCT sequences, summaries and individual test logs. | SR and DT (SBBR/EBBR suites differ) |
| `uefi/` | Logs from UEFI-stage ACS applications, such as BSA/PFDI; **SBSA is part of the SR test flow, not DT**. | SR and DT; SBSA only SR |
| `uefi_dump/` | UEFI Shell diagnostic dumps: boot variables, device handles, memory map, configuration and firmware views. | SR and DT |

Keep the [ACS results parser output](acs_results_structure.md) distinct from the **directory layout** described here: `acs_results_structure.md` documents parsed data fields, not where test evidence is saved.

### `./acs_results/bbsr/` — BBSR (SR and DT, when enabled)

BBSR tests are supported by both SystemReady SR and SystemReady-DT. When BBSR compliance testing is enabled, results may include:

```text
acs_results/bbsr/
├── fwts/                   # BBSR-related FWTS results
├── sct_results/            # BBSR UEFI SCT results
└── tpm2/                   # TPM / measured-boot evidence, if available
```

Keep the folders produced for the run; the presence and contents of `tpm2/` depend on the platform and enabled tests. See the [BBSR ACS verification guide](BBSR_ACS_Verification.md).

### `./acs_results/sbmr/` — SBMR (SR only, when enabled)

For **SystemReady SR**, enabling SBMR in-band execution collects results such as:

```text
acs_results/sbmr/
├── sbmr_in_band_logs/      # collected by the in-band ACS run
└── sbmr_out_of_band_logs/  # collected separately and added manually
```

**Out-of-band (OOB) tests do not run automatically with the in-band ACS run.** Run the OOB tests from their required test environment and copy their logs into `sbmr_out_of_band_logs/`. If only the in-band suite ran, do not present an empty OOB folder as completed testing.

### `./acs_results/network_boot/` — network boot (DT only, when enabled)

SystemReady-DT can capture HTTP/HTTPS boot evidence under `acs_results/network_boot/`, such as the boot console capture and network-boot result logs. These are ACS network-boot results, **not** the separate installed-OS logs. This directory is not a general requirement for every SR run. See the [network boot guide](network_boot_guide.md).

### Other band-specific results

- **SR:** The SR ACS includes **SBSA** tests and associated UEFI/Linux logs when those tests are run. Do not list SBSA as a DT requirement.
- **DT:** Devicetree-specific checks (such as DT validation, kernel selftests, reserved-memory mapping, spin-table or network boot checks) may write their logs under `linux_tools/`, `linux_dump/` or dedicated folders, depending on the ACS image. Do not require these DT-specific logs from SR.

## 2. Additional manually collected results

If automated execution did not capture a required diagnostic, or a test was rerun manually, keep the manual evidence **separate from the original automated output**. The following directory names come from the previous compliance-submission template; they describe how to organize **additional submitted evidence**, not folders guaranteed to exist in `acs_results_template/`.

| Submission location | What to place there | Applicability |
| --- | --- | --- |
| `manual-results/bsa-linux/` | Manual BSA Linux results and console capture; SBSA Linux results only for SR. | BSA: SR/DT; SBSA: SR only |
| `manual-results/bsa-uefi/` | Manual UEFI BSA results; SBSA UEFI results only for SR. | BSA: SR/DT; SBSA: SR only |
| `manual-results/fwts/` | Additional FWTS logs and parameters from manual reruns. | SR/DT (SBBR vs EBBR suites) |
| `manual-results/sct/` | Extra UEFI SCT sequence, logs and console output. | SR/DT |
| `manual-results/uefi_dump/` | Additional UEFI Shell diagnostic logs if automated `acs_results/uefi_dump/` is missing or incomplete. | SR/DT |

The relevant ACS Shell dump script is [`common/uefi_scripts/debug_dump.nsh`](../common/uefi_scripts/debug_dump.nsh). Use the version from the matching ACS media where possible. Record the command, arguments, ACS version and reason for each manual rerun.

## 3. Platform documents and firmware evidence

The following are **supporting submission categories**, not additional ACS test suites. The top-level `docs/` mentioned here is the *submitted platform documents folder*, not this repository's source `docs/` directory.

| Submission location | What to include |
| --- | --- |
| `report.txt` | Platform and firmware identification, OS and ACS versions, test setup, and a checklist of submitted evidence. Fill in the details of the system actually tested. |
| `docs/` | Hardware/firmware manuals, board documentation, build or configuration instructions and supporting information. |
| `fw/fw-image-files/` | Tested firmware binaries/sources, build identifiers, and related BMC/SCP/MCP firmware versions where applicable. |
| `fw/screenshots/` | Relevant setup/boot menus, UEFI configuration, ACPI or Devicetree selection, BMC/U-Boot screens, and other firmware evidence. |
| `fw/uefi-shell-cmds-logs/` | Additional manually captured Shell outputs (for example `dh -d -v`, `bcfg boot dump -v`, `ifconfig -l` and, **on ACPI systems where tables exist**, `acpiview`). |

Keep firmware evidence consistent with the firmware revision used for the ACS test. A DeviceTree system should **not** be expected to supply ACPI DSDT/SSDT dumps when those tables are not implemented.

## 4. Installed operating-system results — `./os-logs/`

`os-logs/` contains **OS installation/boot evidence and diagnostics run on the installed OS**, rather than inside the ACS live environment. Identify each OS by distribution and version and retain its serial console capture separately from any generated diagnostic files.

- **SystemReady SR:** Testing on **RHEL and SLES/SLE** is required for the SR compliance workflow described by the existing template; additional distributions are recommended.
- **SystemReady-DT:** Do **not** apply the SR RHEL/SLES requirement automatically. Submit the installed-OS evidence required by the selected DT compliance test plan.
- **WinPE / other OSes:** Include boot, command output and any associated driver/device logs when those OS tests are performed.

An example of Linux and WinPE results is:

```text
os-logs/
├── linux-rhel-<version>/                # SR example
│   ├── console.log                     # recorded separately
│   └── systemready-band-compliance-logs/
│       ├── dmesg.txt
│       ├── ethtool-test.log
│       └── read_write_check_blk_devices.log
├── linux-sles-<version>/                # SR example
│   ├── console.log
│   └── systemready-band-compliance-logs/
└── winpe-<version>/                    # when tested
    ├── console.log
    └── device_driver_winpe.log
```

The example only shows selected files. **Do not create fake output files**: include the logs actually produced, with failures and warnings intact. A separate serial capture (`console.log`) is not created by the Linux diagnostics script.

For the **Linux ZIP download, `linux_init.sh --mode os` commands, output archive location, network/block-device checks, WinPE `device_driver_winpe.bat` download and log collection**, use the single detailed guide:

**[OS Scripts — Linux and WinPE (`common/os_scripts/README.md`)](../common/os_scripts/README.md)**

## 5. Before submitting

Keep the complete `acs_results/` output, identify the tested band and ACS release, include the platform/firmware details, and associate any manual retests and installed-OS logs with the same system configuration. Preserve original failures and warning logs; a successful summary alone is not sufficient evidence of an entire run.
